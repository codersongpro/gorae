# 운영 열쇠(관리 열쇠·검수 열쇠) 준비와 보관

고래곳간의 신뢰 경계는 교사고래 PIN이 아니라 **검수 서명**입니다. 그 맨 위에 관리(root) 열쇠가 있습니다.

```
관리 개인 열쇠 (root private key)   → 오프라인 보관. 저장소·사이트·확장앱 어디에도 없음
관리 공개키   (root public key)    → extension/core/rootkey.js (확장앱·웹 뷰어·검수 도구가 같이 씀)
        │ 서명
        ▼
고래 족보 site/reviewers.json      → 파수꾼고래 공개키 명부 (버전이 있고, 낮은 버전은 거부)
이달의 고래자리 catalog.featured   → 관리 열쇠 서명
        │
        ▼
파수꾼고래 검수 열쇠                → 작품마다 검수 서명(tailprint)
```

## 1. 관리 열쇠 만들기 (한 번)

저장소 **밖** 폴더를 정합니다(예: `C:\Users\<이름>\gorae-keys`). 도구는 저장소 안 폴더를 거부합니다.

```powershell
$env:GORAE_ROOT_PASSPHRASE = '<12자 이상, 다른 곳에 쓰지 않는 암호>'
$env:GORAE_REVIEWER_PASSPHRASE = '<12자 이상, 다른 암호>'
node tools/keys.mjs init --dir $HOME\gorae-keys --reviewer-id guard-2 --reviewer-name 푸른물결
```

만들어지는 파일:

| 파일 | 내용 | 보관 |
| --- | --- | --- |
| `root.keybackup.json` | 관리 개인 열쇠 (PBKDF2 310,000회 + AES-GCM 암호) | 오프라인 2부 |
| `root.public.jwk` | 관리 공개키 | 공개해도 됨 |
| `reviewer.keybackup.json` | 첫 파수꾼고래 검수 열쇠 (암호) | 파수꾼고래 본인 |
| `reviewer.public.jwk` | 검수 공개키 | 공개해도 됨 |
| `PASSPHRASES-오프라인으로-옮기기.txt` | 환경 변수를 주지 않았을 때만 생기는 임의 암호 | **종이·암호 관리자로 옮긴 뒤 지우기** |

> 2026-10-03 공모전 준비 중에 이 절차로 `C:\Users\dungs\gorae-keys`에 열쇠를 만들었습니다(관리 공개키 지문 `sha256:d1622722522c8035`, 파수꾼고래 `guard-2 푸른물결`). 암호 파일을 오프라인으로 옮기고 지워 주세요.

## 2. 공개키 반영과 다시 서명

```powershell
node tools/keys.mjs apply --dir $HOME\gorae-keys   # extension/core/rootkey.js 갱신 (공개키·지문만)
$env:GORAE_KEY_DIR = "$HOME\gorae-keys"
node tools/build-sample.mjs                         # 족보·샘플 목록·고래자리 다시 서명
npm test                                            # sync + 전체 시험
```

`build-sample.mjs`는 열쇠를 만들지 않고, 코드의 관리 공개키와 열쇠 폴더의 열쇠가 다르면 멈춥니다.
족보 버전은 이전 버전보다 낮아지지 않게 올립니다(확장앱은 이미 본 버전보다 낮은 족보를 거부합니다).

## 3. 백업

- `root.keybackup.json` 은 USB 2개 등 **서로 다른 장소 2곳**에 둡니다. 클라우드 동기화 폴더·메신저·이메일에 올리지 않습니다.
- 암호는 백업 파일과 **다른 곳**에 둡니다.
- 저장소 `.gitignore`가 `*.keybackup.json`, `*.private.jwk`, `PASSPHRASES*.txt`, `tests/keys/`를 막지만, 애초에 저장소 안에 두지 않는 것이 원칙입니다. `tests/rootkey.test.mjs`가 사이트·확장앱 폴더에 개인 열쇠가 섞이지 않았는지 검사합니다.

## 4. 고래 족보 서명 (파수꾼고래 추가·말소)

1. 새 파수꾼고래가 검수 도구 `review.html` → **검수 서명 만들기**에서 열쇠를 만들고 공개키 묶음을 보냅니다.
2. 관리자가 검수 도구 → **고래 족보 관리**에서 `root.keybackup.json`과 암호로 관리 열쇠를 불러옵니다.
3. 공개키를 추가(또는 말소)하고 버전을 올려 서명 → `reviewers.json`을 `site/`에 올립니다.
4. 관리 열쇠는 쓰고 나면 브라우저 탭을 닫습니다(꺼낼 수 없는 형태로만 메모리에 있음).

파수꾼고래는 검수 도구 로그인 때 **자기 검수 열쇠 백업 파일 + 백업 암호**를 씁니다. 사이트에는 어떤 열쇠 백업도 올리지 않습니다.

## 5. 분실·유출 대응

| 상황 | 영향 | 대응 |
| --- | --- | --- |
| 파수꾼고래 검수 열쇠 분실 | 그 고래가 새 서명을 못 함, 기존 서명은 유효 | 새 열쇠를 만들어 족보에 추가. 남이 가져갔을 가능성이 없으면 옛 열쇠를 '탈퇴·전근'(`left`)으로 말소해 이전 서명 유지, 가능성이 있으면 '열쇠 분실'(`lost`, 모두 무효)로 말소 |
| 파수꾼고래 검수 열쇠 유출 | 그 이름으로 위조 가능 | 즉시 `leaked` 사유로 말소한 족보 게시(그 열쇠의 모든 서명 무효) → 필요한 작품 다시 검수 |
| 관리 열쇠 백업 1부 분실 | 남은 1부로 운영 | 새 관리 열쇠로 교체 준비(아래) |
| 관리 열쇠 유출 또는 2부 모두 분실 | 가짜 족보로 위조 가능 / 족보 갱신 불가 | `tools/keys.mjs init`으로 새 관리 열쇠 → `apply` → 족보·고래자리 다시 서명 → **확장앱 새 버전 배포 + 사이트 재배포**. 옛 공개키를 가진 확장앱은 새 족보를 믿지 않으므로 업데이트 안내 필요 |

## 6. 시험 열쇠와의 관계

`tests/keys/`(무시 대상)에는 예전 개발용 시험 열쇠가 남아 있을 수 있습니다. 지금 코드는 이 열쇠를 쓰지 않습니다.
예전에 사이트에 있던 `site/reviewer.keybackup.json`(시험 검수 열쇠를 고정 비밀번호로 잠근 파일)과 그 비밀번호 로그인은 제거했습니다.
